# Country Search — архитектурные решения

## 1. Отмена HTTP-запросов

В приложении используется `AbortController` для отмены предыдущего HTTP-запроса при изменении поискового запроса пользователем.

Когда пользователь вводит новое значение, предыдущий запрос отменяется немедленно. Отмена прекращает уже начатый запрос, а debounce предотвращает запуск нового запроса до завершения паузы ввода. Это два разных механизма.

Для управления временем выполнения запросов используются:

- `AbortController` — позволяет отменить запрос при новом вводе пользователя.
- `AbortSignal.timeout()` — автоматически создаёт сигнал отмены, если запрос выполняется дольше установленного времени.
- `AbortSignal.any()` — объединяет сигналы отмены в один.

Таким образом, приложение различает две ситуации:

- `AbortError` — запрос отменён из-за нового ввода пользователя. Это ожидаемое поведение, поэтому ошибка не отображается.
- `TimeoutError` — время ожидания ответа превышено. Такая ошибка передаётся обработчику ошибок и отображается пользователю.

Перед отображением результатов приложение дополнительно проверяет, не был ли запрос отменён. Это предотвращает вывод результатов устаревших запросов.

## 2. Использование debounce

В приложении реализована собственная функция `debounce`, которая уменьшает количество HTTP-запросов к API.

Задержка составляет 300 миллисекунд.

Без debounce каждый введённый символ приводил бы к отдельному запросу к серверу. Это увеличивало бы количество запросов и создавало лишнюю сетевую нагрузку.

Задержка в 300 мс обеспечивает баланс между отзывчивостью интерфейса и количеством запросов. Пользователь получает время на ввод поискового запроса, при этом поиск остаётся достаточно быстрым.

Функция использует `setTimeout` и `clearTimeout`. При каждом новом вызове предыдущий таймер сбрасывается. Callback выполняется только после того, как в течение заданного времени не поступают новые вызовы.

## 3. Оценка сложности алгоритмов (Big O)

### Функция debounce

Создание или сброс таймера выполняется за O(1).

Функция хранит только один идентификатор таймера, поэтому дополнительная сложность по памяти составляет O(1).

### Функция mapCountryResponse

Функция преобразует данные, полученные от API, в структуру `CountryCard`, используемую приложением.

Доступ к отдельным свойствам объекта выполняется за O(1).

Обработка массивов языков, граничащих стран и валют зависит от количества элементов в каждом массиве.

Если:

- L — количество языков;
- B — количество граничащих стран;
- C — количество валют,

то временная сложность преобразования составляет:

O(L + B + C)

Дополнительная сложность по памяти также составляет O(L + B + C), поскольку при преобразовании создаются новые массивы и значения.

### HTTP-запросы

Время выполнения HTTP-запросов зависит от скорости сети, доступности сервера и времени обработки запроса API. Поэтому его нельзя выразить фиксированной оценкой Big O для локального алгоритма приложения.

## 4. Принципы Clean Code

При разработке приложения применялись следующие принципы чистого кода.

### Принцип единственной ответственности (Single Responsibility Principle)

Каждый модуль отвечает за отдельную задачу:

- `debounce.ts` — управление отложенным выполнением функции.
- `searchCountries.ts` — взаимодействие с API стран.
- `HttpError.ts` — представление HTTP-ошибок.
- `mapCountryResponse.ts` — преобразование и нормализация данных API.
- `app.ts` — управление поиском, debounce, отменой запросов и обработкой ошибок.
- Компоненты UI — создание отдельных элементов интерфейса.
- `main.ts` — объединение логики приложения и пользовательского интерфейса.

### Разделение ответственности (Separation of Concerns)

Взаимодействие с API, преобразование данных, управление логикой приложения и работа с DOM разделены между отдельными модулями.

Такой подход упрощает понимание, тестирование и дальнейшее сопровождение проекта.

### Чистые функции (Pure Functions)

Функция `mapCountryResponse` преобразует входные данные в нормализованный объект страны. Она не изменяет исходные данные и не обращается к внешнему состоянию.

Чистые функции проще тестировать, поскольку их результат зависит только от входных аргументов.

### Типизация (Type Safety)

В проекте используются интерфейсы TypeScript и явные типы параметров и возвращаемых значений.

Это помогает описывать структуру данных и обнаруживать ошибки типов ещё на этапе разработки.

### Обработка ошибок (Error Handling)

Для HTTP-ошибок создан собственный класс `HttpError`.

Отмена запроса, превышение времени ожидания и другие ошибки обрабатываются отдельно. Благодаря этому ожидаемая отмена запроса не воспринимается приложением как ошибка.

### Разработка через тестирование (Test-Driven Development, TDD)

При разработке проекта использовался подход TDD:

1. Сначала создавались тесты для ожидаемого поведения.
2. Затем реализовывалась необходимая функциональность.
3. После этого запускались тесты и проверялось их прохождение.
4. При необходимости выполнялся рефакторинг кода.

Для тестирования используется Vitest. Проверяются отдельные функции, HTTP-запросы, работа с таймерами и отмена запросов.

## 5. Тестирование

В проекте предусмотрены тесты для проверки:

- Работы функции debounce.
- Успешных ответов API.
- HTTP-ошибок и ответов со статусом 404.
- Преобразования данных стран.
- Отмены HTTP-запросов.
- Обработки `AbortError` и `TimeoutError`.
- Работы контроллера поиска и предотвращения лишних запросов.

Для проверки асинхронного поведения используются mock-функции, поддельные таймеры и имитация HTTP-запросов.

На момент подготовки документации проект содержит 26 автоматических тестов в 5 тестовых файлах. Все тесты успешно проходят.
